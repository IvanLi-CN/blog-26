# Style Playbook publishing

The blog reads stable, sanitized Release assets from the private `IvanLi-CN/style-playbook-skills` repository. Content deployments use the currently deployed renderer; console follows the successful blog deployment through a persistent public snapshot. Neither visitors nor console need source credentials.

## Activation

Production activation is separate from implementation. Merge both repository PRs first. Store one fine-grained PAT as the blog Actions secret `PLAYBOOK_SOURCE_TOKEN`, scoped to `Contents: read` on `style-playbook-skills`. The blog discovers releases through its scheduled reconciliation, so the upstream repository needs no blog `Actions: write` credential.

Use a stable upstream Release with both public assets and an archive matching [the public package contract](../specs/style-playbook-integration/contracts/public-package.md). Set blog `PLAYBOOK_INTEGRATION_ENABLED=true`, then use the native stable minor application release for the initial frontend/backend capability deployment. If no public pointer exists yet, the build selects the highest ready stable SemVer Release and validates its manifest, tag commit, and bundle before use; no Release ID needs to be configured. Once a deployed pointer exists, ordinary application builds preserve that adopted source.

The initial frontend artifact carries its validated archive into the locked deployment job. When frontend and backend publish together, the deployment job uploads the complete `playbook-edition.json` seed produced by its final locked rebuild, so the backend package carries the exact edition and public snapshot identity used by the deployed static build; if the frontend deployment is skipped, the backend uses the frontend build seed, and a backend-only release obtains content through the normal pointer or latest-ready-release path. Subsequent normal frontend deployments rebuild with the current public package inside `blog26-edgeone-production`, preserving the existing main-head, media, PWA and proxy gates. The unified image and backend runtime archive wait for that deployment, then join the same production lock; the image consumes the deployed frontend seed as its required, immutable Playbook input, while a backend-only image first materializes the current pointer (or latest ready stable bundle) into the same seed file. The backend packages the same seed, so content updates cannot interleave with their public data. Verify the pointer at `https://ivanli.cc/_content/playbook/manifest.json` and the initial console SSR content, then set `PLAYBOOK_CONTENT_UPDATES_ENABLED=true` to start scheduled updates.

## Update and retry

The blog checks the upstream repository every hour at minute 17. Scheduled and default manual runs use `mode=reconcile`, which accepts no caller-selected source fields and selects the highest ready stable SemVer. Operators may use `mode=release` for an explicit, identity-checked retry. The blog verifies the Release and tag commit independently. GitHub scheduling may be delayed, so this is not a deadline guarantee.

The production job locks before reading deployed state and building. Repeated/already-adopted or older releases skip. The same Release with changed content is rejected. Content builds consume the deployed article/Memo snapshot and fixed deployed renderer. They run the existing static/media/PWA gates, retain current/previous public data and original archives, deploy the complete site and verify the new public pointer. They create no application tag, Release or image. Failed source checks/builds leave deployment untouched; failed EdgeOne deployment is reported by the provider; pointer verification failure requires inspection of the deployed identity before retrying.

## Explicit rollback

Set `PLAYBOOK_CONTENT_UPDATES_ENABLED=false` and wait for any in-flight content run to finish. This pause is required so the next scheduled reconciliation does not immediately undo the deliberate rollback. Then dispatch `playbook-content-rollback.yml` with the exact old stable Release ID/tag/commit/bundle digest. The target tag must be lower than the currently deployed stable tag; the consumer rechecks this after building and before deployment. Rollback is unavailable through the normal update interface. The rollback workflow refuses to run while automatic updates are enabled, validates the old package through the same source/format checks, and rebuilds all pages/data using the current renderer. A schema-incompatible package fails before deployment. The lock keeps rollback and normal application deployment serial.

Verify the adopted source and renderer in the public pointer and Actions summary. Explicitly restore automatic updates only after reviewing the next ready upstream candidate; reconciliation may otherwise undo a deliberate rollback.

## Console and local validation

The default cache directory is `playbook-cache` beside `DB_PATH`; override it with `PLAYBOOK_CACHE_DIR`. `PLAYBOOK_MANIFEST_URL` overrides the public pointer URL. `PLAYBOOK_SEED_PATH` overrides the packaged seed. Production starts an immediate background check and polls every 300 seconds; `PLAYBOOK_SYNC_ENABLED=false` disables networking for controlled local tests. No page request fetches the source. Atomic cache adoption retains current and previous editions. A missing/incompatible download preserves the last compatible edition; no usable cache or seed affects only the Playbook surface.

For an offline fixture build, run `bun tests/lib/playbook-fixture.ts`, set `PLAYBOOK_BUNDLE_DIR` to that output, set `DB_PATH` and `LOCAL_CONTENT_BASE_PATH` to controlled local data, and run `bun run site:build`. `bun scripts/verify-playbook-artifact.ts` checks page/data/resource identity. Console and static builds can be checked together with `bun tests/lib/playbook-build-smoke.ts` after both artifacts are built. Heavy builds/regression/E2E work runs on codex-testbox under the repository's shared-testbox policy.
