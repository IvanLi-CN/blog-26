# Style Playbook publishing

The blog reads stable, validated Release assets from the private `IvanLi-CN/style-playbook-skills` repository. Content deployments use the currently deployed renderer; console follows the successful blog deployment through a persistent public snapshot and a protected source-bound supplement receiver. The Blog export path does not rewrite or sanitize shared Playbook prose. Neither visitors nor console need source credentials.

## Activation

Production activation is separate from implementation. Merge both repository PRs first. Store one fine-grained PAT as the blog Actions secret `PLAYBOOK_SOURCE_TOKEN`, scoped to `Contents: read` on `style-playbook-skills`, and a separate `PLAYBOOK_SUPPLEMENT_SYNC_TOKEN` secret accepted only by the console receiver. Optionally set `PLAYBOOK_SUPPLEMENT_SYNC_URL`; it must be a credential-free HTTPS URL, otherwise the workflow uses `/api/admin/playbook/supplement` on `PUBLIC_API_BASE_URL`. The blog discovers releases through scheduled reconciliation; the upstream repository may also use the existing dispatch contract as an acceleration path.

Use a stable upstream Release with both public assets and an archive matching [the public package contract](../specs/style-playbook-integration/contracts/public-package.md). Set blog `PLAYBOOK_INTEGRATION_ENABLED=true`, then use the native stable minor application release for the initial frontend/backend capability deployment. If no public pointer exists yet, the build selects the highest ready stable SemVer Release and validates its manifest, tag commit, and bundle before use; no Release ID needs to be configured. Once a deployed pointer exists, ordinary application builds preserve that adopted source.

The initial frontend artifact carries its validated archive into the locked deployment job. When frontend and backend publish together, the deployment job uploads the complete `playbook-edition.json` seed produced by its final locked rebuild, so the backend package carries the exact edition and public snapshot identity used by the deployed static build; if the frontend deployment is skipped, the backend uses the frontend build seed, and a backend-only release obtains content through the normal pointer or latest-ready-release path. Subsequent normal frontend deployments rebuild with the current public package inside `blog26-edgeone-production`, preserving the existing main-head, media, PWA and proxy gates. The unified image and backend runtime archive wait for that deployment, then join the same production lock; the image consumes the deployed frontend seed as its required, immutable Playbook input, while a backend-only image first materializes the current pointer (or latest ready stable bundle) into the same seed file. The backend packages the same seed, so content updates cannot interleave with their public data. Verify the pointer at `https://ivanli.cc/_content/playbook/manifest.json` and the initial console SSR content. `PLAYBOOK_INTEGRATION_ENABLED=true` enables both application integration and scheduled content updates.

## Update and retry

The blog checks the upstream repository every hour at minute 17. Scheduled and default manual runs use `mode=reconcile`, which accepts no caller-selected source fields and selects the highest ready stable SemVer. Operators may use `mode=release` for an explicit, identity-checked retry. The blog verifies the Release and tag commit independently. GitHub scheduling may be delayed, so this is not a deadline guarantee.

The production job locks before reading deployed state and building. Repeated/already-adopted or older releases skip. The same Release with changed content is rejected. Content builds consume the deployed article/Memo snapshot and fixed deployed renderer. They run the existing static/media/PWA gates, retain current/previous public data and original archives, deploy the complete site and verify the new public pointer, then submit the matching supplement projection, same-source public relation index and verified source bytes (or an explicit empty overlay) to console. They create no application tag, Release or image. Failed source checks/builds leave deployment untouched; failed EdgeOne deployment is reported by the provider; pointer verification or protected supplement receiver failure requires inspection and retry before declaring the update complete.

## Explicit rollback

Set `PLAYBOOK_INTEGRATION_ENABLED=false` and wait for any in-flight content run to finish. This pauses scheduled reconciliation and is required so it does not immediately undo the deliberate rollback. Do not run an application release while the integration is paused. Then dispatch `playbook-content-rollback.yml` with the exact old stable Release ID/tag/commit/bundle digest. When the Release has a supplement, also provide all eight supplement identity inputs from that Release: `supplement_bundle_sha256`, `supplement_manifest_sha256`, `supplement_bundle_asset_id`, `supplement_bundle_asset_digest`, `supplement_bundle_asset_size`, `supplement_manifest_asset_id`, `supplement_manifest_asset_digest`, and `supplement_manifest_asset_size`; obtain them from the validated Release summary or the two supplement manifest/asset records, not by recomputing or guessing values. The target tag must be lower than the currently deployed stable tag; the consumer rechecks this after building and before deployment. Rollback is unavailable through the normal update interface. The rollback workflow refuses to run while integration is enabled, validates the old package through the same source/format checks, and rebuilds all pages/data using the current renderer. A schema-incompatible package fails before deployment. The lock keeps rollback and normal application deployment serial.

Verify the adopted source and renderer in the public pointer and Actions summary. Explicitly restore automatic updates only after reviewing the next ready upstream candidate; reconciliation may otherwise undo a deliberate rollback.

## Console and local validation

The default cache directory is `playbook-cache` beside `DB_PATH`; override it with `PLAYBOOK_CACHE_DIR`. `PLAYBOOK_SEED_PATH` overrides the packaged seed. Production uses the fixed public pointer and starts an immediate background check, then polls every 300 seconds; `PLAYBOOK_SYNC_ENABLED=false` disables networking for controlled local tests. The protected supplement receiver stores a source-bound `supplement-state.json` beside the public cache with mode `0600`; it stages data before public adoption, and admin reads merge it only after source identity matches. No page request fetches the source. Atomic cache adoption retains current and previous editions. A missing/incompatible download preserves the last compatible edition; no usable cache or seed affects only the Playbook surface.

For an offline fixture build, run `bun tests/lib/playbook-fixture.ts`, set `PLAYBOOK_BUNDLE_DIR` to that output, set `DB_PATH` and `LOCAL_CONTENT_BASE_PATH` to controlled local data, and run `bun run site:build`. `bun scripts/verify-playbook-artifact.ts` checks page/data/resource identity. Console and static builds can be checked together with `bun tests/lib/playbook-build-smoke.ts` after both artifacts are built. Heavy builds/regression/E2E work runs on codex-testbox under the repository's shared-testbox policy.

## Content and RAG recovery

After applying forward migration 0015, console reconstructs current/previous manifests and durable unfinished jobs before starting polling. Content adoption does not wait for embedding, and startup repair uses only adopted public snapshots and current public blog content. Do not delete old vector rows or infer orphan ownership from slugs. Earlier sync counts and adoption timestamps are unknown unless an atomic task checkpoint exists.

The admin status endpoint separates collection totals from public RAG content/chunk coverage. For retained production vectors without configuration provenance, expect outdated targets; an empty Playbook projection still has an expected unindexed total. This code upgrade does not prove production data has been repaired. Read the actual status first, then explicitly authorize a production `repair` task for blog, Playbook or both. Repair preserves valid chunks and old compatible storage, returns durable task IDs and can be cancelled per task. A rebuild is a separate explicit operation covering every selected target.

Validate recovery by comparing the same scope/edition/configuration identity before and after repair. Content and chunk totals must each equal indexed + unindexed + outdated + failed; complete parents require all expected chunks. Check durable task progress and controlled errors, then confirm modern RAG no longer reports that source as incomplete. Provider failure preserves adopted keyword content. Cancellation preserves successful chunks, and explicit retry or a changed target is required for cancelled manifests. No status GET or ordinary search starts this work. Deployment, production repair and TLS investigation require their own operation scope.
