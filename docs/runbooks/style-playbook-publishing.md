# Style Playbook publishing

The blog reads stable public Release assets from `IvanLi-CN/style-playbook-skills`. Content deployments use the currently deployed renderer; console follows the successful blog deployment through a persistent public snapshot. Neither visitors nor console need source credentials.

## Activation

Production activation is separate from implementation. Merge both repository PRs first. Install two separate GitHub Apps: the upstream notification role needs blog Actions write; the blog source-reader role needs upstream Contents read. For the blog, configure `PLAYBOOK_SOURCE_APP_ID` (variable) and `PLAYBOOK_SOURCE_APP_PRIVATE_KEY` (secret), alongside its existing EdgeOne credentials. Keep the upstream notification switch and `PLAYBOOK_CONTENT_UPDATES_ENABLED` disabled until initial deployment succeeds.

Publish a new stable upstream Release through its native workflow with both public assets. Its archive must match [the public package contract](../specs/style-playbook-integration/contracts/public-package.md). Set blog `PLAYBOOK_INTEGRATION_ENABLED=true` and an explicit `PLAYBOOK_INITIAL_RELEASE_ID`. Use the native stable minor application release for the initial frontend/backend capability deployment. When a deployed pointer already exists, ordinary application builds preserve that adopted source; they do not revert to the initial Release ID.

The initial frontend artifact carries its validated archive into the locked deployment job. When frontend and backend publish together, the deployment job uploads the complete `playbook-edition.json` seed produced by its final locked rebuild, so the backend package carries the exact edition and public snapshot identity used by the deployed static build; if the frontend deployment is skipped, the backend uses the frontend build seed, and a backend-only release obtains content through the normal pointer or initial-bundle path. Subsequent normal frontend deployments rebuild with the current public package inside `blog26-edgeone-production`, preserving the existing main-head, media, PWA and proxy gates. The unified image and backend runtime archive wait for that deployment, then join the same production lock; the image consumes the deployed frontend seed as its required, immutable Playbook input, while a backend-only image first materializes the current pointer (or fixed initial bundle) into the same seed file. The backend packages the same seed, so content updates cannot interleave with their public data. The unified image and backend runtime archive carry a fixed public seed. Verify the pointer at `https://ivanli.cc/_content/playbook/manifest.json` and the initial console SSR content before enabling automatic content updates and upstream notifications. Use the next stable upstream release for the real cross-repository permission/deployment/five-minute-follow-up acceptance.

## Update and retry

Upstream dispatches `playbook-content-update.yml` at blog `main` after uploading the readiness manifest. Dispatch inputs are defined in [release-trigger.md](../specs/style-playbook-integration/contracts/release-trigger.md). The blog verifies the Release and tag commit independently. `mode=reconcile` accepts no caller-selected source fields and selects the highest ready stable SemVer; hourly reconciliation runs at minute 17. GitHub scheduling may be delayed, so this is recovery rather than a deadline guarantee.

The production job locks before reading deployed state and building. Repeated/already-adopted or older releases skip. The same Release with changed content is rejected. Content builds consume the deployed article/Memo snapshot and fixed deployed renderer. They run the existing static/media/PWA gates, retain current/previous public data and original archives, deploy the complete site and verify the new public pointer. They create no application tag, Release or image. Failed source checks/builds leave deployment untouched; failed EdgeOne deployment is reported by the provider; pointer verification failure requires inspection of the deployed identity before retrying.

## Explicit rollback

Set `PLAYBOOK_CONTENT_UPDATES_ENABLED=false`, wait for any in-flight content run to finish, then dispatch `playbook-content-rollback.yml` with the exact old stable Release ID/tag/commit/bundle digest. Rollback is unavailable through the normal update interface. The rollback workflow refuses to run while automatic updates are enabled, validates the old package through the same source/format checks, and rebuilds all pages/data using the current renderer. A schema-incompatible package fails before deployment. The lock keeps rollback and normal application deployment serial.

Verify the adopted source and renderer in the public pointer and Actions summary. Explicitly restore automatic updates only after reviewing the next ready upstream candidate; reconciliation may otherwise undo a deliberate rollback.

## Console and local validation

The default cache directory is `playbook-cache` beside `DB_PATH`; override it with `PLAYBOOK_CACHE_DIR`. `PLAYBOOK_MANIFEST_URL` overrides the public pointer URL. `PLAYBOOK_SEED_PATH` overrides the packaged seed. Production starts an immediate background check and polls every 300 seconds; `PLAYBOOK_SYNC_ENABLED=false` disables networking for controlled local tests. No page request fetches the source. Atomic cache adoption retains current and previous editions. A missing/incompatible download preserves the last compatible edition; no usable cache or seed affects only the Playbook surface.

For an offline fixture build, run `bun tests/lib/playbook-fixture.ts`, set `PLAYBOOK_BUNDLE_DIR` to that output, set `DB_PATH` and `LOCAL_CONTENT_BASE_PATH` to controlled local data, and run `bun run site:build`. `bun scripts/verify-playbook-artifact.ts` checks page/data/resource identity. Console and static builds can be checked together with `bun tests/lib/playbook-build-smoke.ts` after both artifacts are built. Heavy builds/regression/E2E work runs on codex-testbox under the repository's shared-testbox policy.
