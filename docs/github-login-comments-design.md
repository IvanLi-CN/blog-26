# GitHub 登录与公开评论需求设计

本文记录 GitHub 读者登录与公开评论的需求结论、实现边界及仓库依据。产品边界、审核和软删除规则、登录体验、仅在后台提示待审核数量的通知范围，以及响应式断点等默认细节均已确认；产品实现随主题 Spec 交付，外部 GitHub 应用注册、真实授权和生产部署仍需单独完成。

完整需求与逐项验收条件见 [GitHub 读者登录与公开评论 Spec](./specs/github-reader-comments/SPEC.md)，实现状态见 [IMPLEMENTATION.md](./specs/github-reader-comments/IMPLEMENTATION.md)。领域术语见 [GLOSSARY.md](../GLOSSARY.md#公开互动)；读者身份与历史评论的隔离取舍见 [ADR 0029](./adr/0029-github-reader-and-legacy-comment-identity.md)。

## 已确认的目标

- 项目需要支持 GitHub 登录。
- GitHub 登录需要与公开评论功能打通。
- GitHub 登录仅建立用于公开评论及回复的读者身份，与管理员登录及授权无关。
- 博客只有一个管理员；本次不引入多管理员、GitHub 管理员映射或管理员资格配置。
- 读者新发表的评论与回复必须使用 GitHub 登录；评论区不再提供游客自填昵称、邮箱或邮箱验证码登录作为替代入口。
- 评论写入接口必须执行相同的 GitHub 读者身份校验，旧游客会话或普通邮箱登录会话不满足新发评论与回复的准入条件；不能仅隐藏前端入口。
- 历史评论保留内容、原作者署名和审核状态，由管理员继续管理；不因邮箱或昵称相同自动绑定 GitHub 账号，暂不提供读者自助认领。
- GitHub 读者身份与旧邮箱账号保持独立，不根据相同邮箱或昵称自动合并；该身份不继承旧账号对应的评论编辑、删除或管理权限。
- 文章、Memo 和项目详情都需要评论；Memo 包括普通 Memo 与剪藏 Memo，公开评论与剪藏私人 AI 对话保持独立。
- 宽屏时评论区放在正文右侧；其他宽度放在正文下方的卡片中，窄屏按既有移动内容流约定去掉结构性卡片外框。
- Console 中如果评论区与 AI 对话卡片争用同一区域，可以通过 tabs 切换；tabs 不改变 AI 对话现有访问权限。
- 评论身份使用 GitHub 昵称、头像和主页；GitHub 用户未公开邮箱也能使用，不额外要求填写邮箱，不申请读取私有邮箱的权限。
- 新评论与回复均先进入待审核状态，明确标记“待审核”，仅发表者本人和管理员可见；审核通过后才向其他读者显示。
- 管理员可以在内容评论区和后台执行通过或删除；后台支持批量通过与批量删除，管理权限仍来自既有的唯一管理员身份。
- 读者不能修改已提交的评论或回复，无论其处于待审核还是已通过状态；可以删除自己通过 GitHub 身份发表的新评论或回复，不能删除他人的内容，也不能认领或删除历史评论。
- 删除采用软删除，保留记录与回复关联；删除单条评论不连带删除已有回复。有当前读者可见的回复时，原位置仅展示“该评论已删除”的结构占位，不显示原正文或作者资料；没有可见回复则从正常评论列表移除。
- 回复采用“主评论 + 同层回复”的两层展示；读者可以继续互相回复并标注“回复某人”，后续回复仍归于同一主评论，不继续增加缩进。
- 后台提供已删除筛选，仅管理员可以查看软删除记录并恢复；恢复后统一回到待审核，必须再次通过才公开，读者不能自行恢复。
- 登录从评论区发起，当前页面跳转 GitHub 授权，完成后回到原文章、Memo 或项目的评论位置，保留未提交草稿和回复对象，由用户确认提交，不自动发表评论；取消或失败时也保留草稿。
- 本次只在后台提供待审核数量提示与集中处理入口，不增加邮件通知、浏览器推送或站内消息中心，也不为通知额外采集读者邮箱。
- 本次工作整理需求与设计结论，不修改产品实现。

## 读者身份与资料

GitHub 读者身份与评论归属应使用 GitHub 持久用户 ID 关联，而不是可以变化的账号名、显示昵称或邮箱。同一个 GitHub 账号更改用户名或公开资料后仍然是同一个评论发表者；GitHub 授权回调必须从服务端确认当前账号，不能接受浏览器自行声明的作者身份。

公开展示资料只需要昵称、头像和 GitHub 主页，不要求用户公开或提供邮箱，也不因邮箱不可用而阻止登录或评论。公开评论接口不应返回作者邮箱，包括既有历史评论的邮箱。显示名缺失时回退 GitHub 账号名，头像失败时用本地默认头像，资料在成功登录时更新。

## 已确认的登录体验

评论区提供“使用 GitHub 登录”入口，采用当前页跳转授权，不依赖新窗口或弹窗。用户在 GitHub 完成授权后回到发起登录的文章、Memo 或项目详情，并恢复评论位置、尚未提交的正文与回复对象；不因登录成功自动提交评论。授权取消或失败时保留草稿，并允许在原上下文重试；会话过期时同样保留未提交内容。

草稿只需在当前浏览器本地保留，不在登录前上传为服务器草稿，也不要求跨设备草稿同步。草稿必须按内容类型和目标区分，不能误恢复到另一个同名内容或回复对象；若回复对象已被删除或不再可访问，应保留文字并提示用户重新选择目标，不擅自转为主评论发布。

退出读者登录只影响该读者会话，不能撤销或替换唯一管理员的既有身份；GitHub 读者的授权、过期与退出都不改变私人 AI 对话及管理员权限。回跳仅允许实际部署中受信任的公开站、Console 与合法内容位置，不接受任意外部跳转。GitHub 授权凭据由服务端处理，不能附在回跳 URL 或草稿中；公开页依旧通过 Console API 获取读者身份，不把个性化内容写入静态页面或共享缓存。

## 已确认的审核与管理规则

| 评论状态 | 未登录读者 | 发表者本人 | 其他 GitHub 读者 | 管理员 |
| --- | --- | --- | --- | --- |
| 待审核 | 不可见。 | 可见，并标记待审核。 | 不可见。 | 可见，并标记待审核，可通过或删除。 |
| 已通过 | 在所属内容公开可读时可见。 | 可见。 | 在所属内容公开可读时可见。 | 可见，可删除。 |

“当前用户”指该条评论或回复的实际发表者，不是任意当前登录用户。本人可见权限依据稳定的 GitHub 读者身份判断，不能依靠邮箱、昵称或客户端传入的作者字段。历史待审核评论继续由管理员管理，不因新读者资料相同而对其开放。

这套规则适用于文章、Memo、项目的评论和回复，也适用于评论列表、分页、回复加载、单条访问、评论数量与任何公开导出。未授权读者不得通过共享缓存、接口响应、条目计数或通知获得待审核正文及私人状态；需要身份过滤的响应不能被共享缓存后返回给其他身份。

管理员的两处操作入口是内容详情的评论区与后台评论管理，均需提供通过和删除；普通 GitHub 读者不能审核自己或他人的评论。后台覆盖三类评论对象及历史评论，支持显式选择条目后的批量通过、批量删除，并准确反馈处理结果。更新审核状态后，评论区和后台应读取一致的结果，成功提示必须区分“已提交，待审核”和“已通过”。

读者已提交的评论和回复不可编辑；前端不提供编辑入口，服务端也必须拒绝读者修改请求，不能只移除按钮。读者可以删除本人通过 GitHub 身份发表的待审核或已通过内容，归属按稳定身份校验。管理员通过评论与读者删除评论发生并发时，删除结果不能被迟到的通过操作重新公开。

删除操作统一为软删除，包括读者自删、评论区管理员删除与后台单条或批量删除；不硬删除数据库记录，也不级联删除他人的回复。已删除状态独立于原审核状态，普通“通过”操作不能清除删除状态或使已删除正文重新出现。

原评论有当前读者可见的回复时，用“该评论已删除”占位维持讨论关系；该位置不再返回或展示原正文、作者昵称、头像和主页。无可见回复的已删除评论不占正常列表条目或正常评论数量。未经公开的待审核内容不得因软删除而向其他读者暴露占位；所有回复仍需各自满足本人或管理员可见、或已审核通过的规则，删除父评论不能替回复完成审核。

后台提供“已删除”筛选，管理员可以在此查看被软删除的记录及原内容，并恢复指定记录。恢复不修改原正文、不改变原评论对象和回复关系，不连带恢复其他已删除记录；恢复后的评论统一回到待审核，不恢复为原来的已通过状态，必须再次显式通过才对其他读者公开。后台批量通过必须跳过或明确拒绝已删除项，不能把“通过”混同为“恢复”。读者无权查看已删除原文或执行恢复，正常评论区仍只显示必要的无正文、无作者资料占位。

## 已确认的回复呈现

每个讨论组由一条主评论与同层回复组成。回复主评论或回复其中的具体读者都保留对应关系，显示“回复某人”；无论交流往返多少次，界面最多两层，不继续缩进，也不能出现提交成功但因超过两层而无法显示的回复。

主评论和回复均执行相同的 GitHub 身份、待审核、不可编辑与软删除规则。回复对象必须属于同一评论对象和讨论组，不能通过提交其他文章、Memo 或项目的评论 ID 把讨论混在一起。回复目标被软删除后，不得借“回复某人”标签或引用继续展示其已隐藏的作者资料或原文。

新回复仅能面向已通过且未删除的具体评论；待审评论不开放继续回复。主评论软删除后，已有未删除且已通过的具体回复仍可供继续交流，讨论归属保留在原主评论下，不重新创建主评论或恢复已删除正文。

## 已确认的布局与可见性边界

| 场景 | 评论区域 | 已有内容与权限 |
| --- | --- | --- |
| 宽屏文章、Memo 和项目详情 | 正文右侧区域。 | 保持正文可读宽度，不能为放入评论而让正文或评论栏不可用。 |
| 不足以并排的非窄屏详情 | 正文下方的独立评论卡片。 | 继续使用 Nature 阅读与交互风格，避免卡片套卡片。 |
| 窄屏详情 | 正文下方的连续评论区，无结构性卡片外框。 | 继承现有低于 640px 的移动阅读承载层与触控尺寸约定，保留表单控件所需的边界。 |
| Console 中公开评论与 AI 对话争用区域 | 允许在相应区域使用“评论 / AI 对话”tabs。 | 仅向原本有 AI 对话权限的身份提供该能力；普通读者只获得公开评论，不因域名或 GitHub 登录获得私人对话。 |

结合现有正文宽度、项目侧栏和剪藏 AI 栏，以 1280px 为并排断点，优先采用 320–360px 互动栏；它不同于“窄屏去卡片”的 640px 既有边界。项目原有外部链接和目录仍需保留。非宽屏评论位于正文下方，AI 保持既有独立交互及窄屏底部抽屉，不能将私人对话混入公开评论或评论提交中。

本功能扩展公开内容的互动；不会让 GitHub 读者获得私有、草稿 Memo、私人剪藏讨论或管理界面的访问权。评论对象必须区分文章、Memo 与项目，不能仅因 slug 相同而共用讨论；文章的历史评论仍保留原文章归属。

## 布局核对发现

- 剪藏 AI 对话目前以 1024px 为并排断点，右侧对话栏为 320–360px；更窄时通过底部抽屉进入。剪藏 Spec 的 REQ-MCL-009 已增加评论布局的主题归属；独立 AI 卡和无评论访客单栏保留其适用条件，新增评论的详情按本主题组合，权限约定保持原样。
- 项目现有侧栏包含公开链接和目录，并在低于 1024px 时排到正文之前。评论不能直接随该侧栏一起前置，中等及窄屏必须明确保留正文下方的评论位置。
- Console 的剪藏实际阅读入口位于 `PublicMemoAuthoring` 内部的 `ClippingDetail`，只修改静态 Memo 页面不能覆盖真实 Console 场景。切换 tabs 与改变窗口宽度时需要保留未发送评论草稿、私人 AI 对话草稿、消息及生成状态。
- 项目可能只有 catalog 记录而没有 posts 表记录，评论对象校验必须支持此类公开项目。文章、Memo 和项目的 slug 未保证跨类型唯一，不能只靠原评论表的 `postSlug` 扩展。
- 当前公开 tabs 基础组件存在值传递及键盘语义方面的覆盖缺口；后续实现需验证或补齐可访问性，不能仅靠视觉切换隐藏内容。

| 管理员 | 登录用户与管理员具有独立权限判定，生产与开发的提权规则也有区别。 | GitHub 读者身份必须与唯一管理员身份隔离，不能因邮箱、昵称或其他公开资料相同而取得管理权限。 |
| 作者展示 | 头像由邮箱生成 Gravatar；评论查询仍返回顶层作者邮箱。 | 新读者改用 GitHub 昵称、头像和主页，不要求邮箱；公开接口需去除邮箱暴露。 |
| 发布与审核 | 创建代码直接发布为 approved，成功提示却称等待审核；已有管理和批量操作路径。 | 创建改为待审核，仅本人和管理员可见；修正列表状态投影与权限过滤，确保评论区和后台均可通过、删除，后台批量操作覆盖三类对象。 |
| 回复与删除 | 列表只组织两层；创建未严格验证父评论，删除为单条硬删除且未处理子回复。 | 保持两层展示，补齐回复目标和讨论组校验；改为单条软删除，保留回复与必要占位；后台增加已删除筛选与管理员恢复，恢复后待审核。 |
| 通知 | 评论创建链路中的邮件通知仍为 TODO。 | 已确认仅做后台待审核数量与集中入口，不补建邮件、推送或消息中心。 |
| Web Demo | 评论读取为空，创建只返回模拟成功，缺少完整持久的评论交互。 | 后续实现的演示与验收需要覆盖真实产品状态转换。 |

## 部署约束

公开站是静态发布面；Console 承担运行时 API 与认证。现有约定要求认证 Cookie 限定在 Console host，公开域名的回源请求剥离身份；评论客户端支持通过公开 API base URL 直接请求 Console，并携带 Cookie。接入设计必须同时覆盖公开站发起登录、Console 完成回调、会话读回、回到原文章和评论位置，以及后台身份隔离，不能通过扩大 Cookie 域或放松公开回源身份边界隐式解决。

以上边界来自 [ADR 0010](./adr/0010-self-contained-console-runtime.md) 与当前代码。规范据此要求授权与回调归 Console 管理、回跳使用可信内容位置、环境凭据隔离；未配置或授权失败时保留阅读和草稿，不回退游客发言。

授权协议校验、可信回跳、软删除并发处理、缓存隔离及可控 Web Demo 属于让已确认行为成立所需的技术边界，验收条件已在 Spec 对应需求中列明。GitHub 应用注册形式和具体库可在这些边界内选择，不增加读者所需权限，也不代表本次已注册外部应用。

## 官方资料核验

- GitHub 的 [Web application flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#web-application-flow) 支持浏览器授权码流程、state 与 PKCE S256。产品不需要自行收集 GitHub 密码。
- [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps#available-scopes) 允许不申请额外 scope 读取公开身份资料；私有邮箱需要额外权限。是否采集邮箱应由需求决定，不默认申请仓库访问权限。
- [用户 API](https://docs.github.com/en/rest/users/users#get-a-user-using-their-id) 区分持久的用户 ID 与可以变化的 login，公开邮箱可以为空。因此用户名和公开邮箱不能被默认当成永久身份键。
- GitHub 应用注册形式属于实现选择；产品边界固定为最少公开身份资料、不要求私有邮箱、仓库权限或安装。本次官方资料核验仅界定可行性。

## 运行配置

GitHub 读者 OAuth 使用独立 OAuth App。服务端需要配置 `GITHUB_READER_CLIENT_ID`、`GITHUB_READER_CLIENT_SECRET` 和 `GITHUB_READER_CALLBACK_URL`；生产回调固定为 `https://console.ivanli.cc/api/public/reader-auth/github/callback`，测试环境使用当前隔离 Console 的回调地址。配置不完整时登录入口返回不可用状态，既有管理员认证不受影响。
