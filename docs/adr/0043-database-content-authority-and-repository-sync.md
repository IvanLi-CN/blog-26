# ADR 0043：数据库内容权威与内容仓库双向同步

- Status: accepted

## 背景

文章与 Memo 长期存在两个写入者：管理端编辑器直接写数据库，而本地文件源按修改时间扫描并回填数据库。数据库行的 `dataSource` 仍记为 `local`，因此一次全量同步会按来源名判废并删除这些行；文件被触碰后，增量同步又会把库内改动覆盖回去。内容同时没有可核对的异地副本。Style Playbook 已经确立「从 GitHub 读取并采用快照」的方向，本决定是相反方向的边界：内容从数据库出发，与一个对等仓库同步。

## 决定

数据库内容库是文章、Memo 与剪藏材料的唯一权威。私有 GitHub 内容仓库是对等副本，不是只写镜像。内容引用的媒体文件保存在本地媒体存储，由内容库记录其路径、sha 与大小，并作为文件系统上的字节归属。

与内容仓库的全部交互只经 GitHub API：解析 ref、递归读取树、按 sha 读取 blob、用 Git Data API 生成单个提交并更新 ref。服务端不克隆仓库、不在磁盘创建可写内容树、不把凭据写入文件、不依赖 `git` 可执行文件。生产运行镜像只安装 `curl`、`ca-certificates`、`sqlite3`、`gosu` 与运行库，本决定不为内容同步引入新系统依赖。

同步是双向的，冲突通过差异对比与人工裁决解决，任何一侧都不自动覆盖另一侧。三方合并的共同祖先是我们保存的同步基线——该内容的规范化正文与 frontmatter——而不是仓库的提交历史。规范化形态（固定字段与顺序、统一换行、统一媒体引用）因此成为正确性要求：没有它，每次推送后立刻拉取都会看到差异。

权威切换必须在一个发布内原子完成：先在停机窗口一次性导入，再同一发布停止注册本地内容源、停止内容扫描任务并移除判废路径。迁移期间不得改变已注册来源集合、扫描根、判废谓词或权威写入者。

## 考虑过的方案

- **服务端本地 clone + `git merge`。** 被否。需要新增 `git` 依赖、凭据落盘、额外持久卷与第二份可写内容树；`git merge-base` 给出的祖先内容也不等于我们规范化后的形态，frontmatter 仍要自己按字段合并。
- **只写镜像（单向推送）。** 被否。仓库需要能作为编辑面，漂移必须是可合并的输入而不是需要强制覆盖的错误。
- **逐文件 Contents API 提交。** 被否。批量推送会变成逐文件提交，破坏「一批一次提交」与可回滚语义。
- **分阶段切换，先让数据库接手文章。** 被否。每 30 分钟运行的增量任务会把数据库改动按文件回填，全量同步会按来源判废删除数据库行。

## 后果

- 媒体文件留在本地媒体存储，不进入数据库：附件体积会放大 sqlite 备份，而且内容读取与推送都需要字节。代价是库与磁盘可能出现分歧，因此内容库必须记录每个附件的 sha 与大小，并在推送与差异比较前核对实际文件；不一致或缺失时受控失败。该目录不得被扫描为内容源。
- frontmatter 的字段顺序与缺值省略从风格问题升为契约。
- 管理端内容文件树与内容文件读写接口退役，编辑器只编辑库内内容。
- 拉取走 API，与本地内容扫描互不相干，因此迁移期间不会改变扫描范围。
- 仓库侧改名在 API 层表现为删除加新增，需要按内容 hash 配对或由管理员确认。
- 内容仓库增长到 GB 级时再评估 partial clone；当前媒体上限使该阈值不构成近期问题。
