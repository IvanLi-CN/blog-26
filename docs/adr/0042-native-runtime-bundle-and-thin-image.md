# 原生产物与薄运行镜像

## Context

镜像构建在 Docker 内重复安装完整开发依赖、编译搜索模块、编码图片和构建应用；预构建入口也会重新安装完整依赖。容器缓存传输与应用构建耦合，无法把镜像打包成本和真实编译成本分别核验。发布工具还必须保留冻结输入和已发布产物的不可替换身份。

## Decision

所有新镜像产物在 Ubuntu 24.04 amd64 原生 runner 上构建，并形成经过验证的 runtime bundle。Dockerfile 只安装操作系统运行依赖并复制 bundle，Bun donor 只提供固定版本二进制；构建与运行使用相容的 Ubuntu 基线。既有两个 target 保留为只打包的别名，不提供容器内编译回退。

bundle 声明来源 SHA、构建身份、配置、锁文件、工具链、平台、镜像 digest 和逐文件摘要。消费者绑定可信来源和预期身份，验证完整性、安全路径、原生 ELF 与动态库要求后才能打包。生产依赖在原生 staging 使用冻结锁文件安装；运行时实际使用的依赖必须归入生产依赖，不能靠复制开发环境掩盖缺失。

冻结发布输入以 schemaVersion 2 显式记录新运行配方，保留 v1 读取和既有产物原字节恢复。旧 identity 不得改用新配方重建或覆盖；历史源码按原配方隔离回放。发布版本、触发和部署权限不因构建迁移改变。

## Consequences

CI、发布与本地打包消费同一产物接口；镜像生产者固定原生平台。本地其他平台必须提供匹配的已验证 bundle，不能隐式容器编译。镜像缓存只保存薄运行层，编译和图片缓存保持各自输入边界。收益必须计入原生准备、传输、打包、加载、smoke 和清理，并同时证明 Docker 暖 job 至少降低 25% 及完整 workload runner total 不增加。

## Rejected alternatives

仅把编译移出 Docker 而继续复制完整开发依赖，无法证明生产依赖闭包，也增加镜像传输。使用 QEMU 或 job 容器编译不符合原生平台构建边界。统一重建旧冻结身份会破坏原产物恢复契约。
