# 产品预发布的版本目标与向前分配

产品版本请求先确定语义目标，再确定完整版本。语义升级以可信的已发布正式产品版本及其来源为基线，按整个待发布区间的最高 verified impact 求得必要的主、次、补丁版本；预发布不能取代这个正式语义基线。完整 SemVer 排序则包含所有已发布、预留和废弃的版本，保证新身份向前且不复用已占用版本。这两项校验分别进行，避免将 `2.8.0-alpha.1` 低于正式 `2.8.0` 误判为未满足 minor 目标。

当语义升级没有要求更高目标时，alpha、beta、rc 和正式请求沿用当前尚未结束的预发布核心版本。以正式基线 `2.7.0` 和已验证 minor 为例，请求可以形成 `2.8.0-alpha.1 → 2.8.0-alpha.2 → 2.8.0-beta.1 → 2.8.0-rc.1 → 2.8.0`。同一阶段自动序号从 1 开始，按已占用序号递增；切换到更后阶段从该阶段尚未占用的下一序号开始。允许跳过阶段和直接发布正式版，不要求先经历每个阶段。

同一目标进入 beta 后自动 alpha 请求必须停止；进入 rc 后自动 alpha 或 beta 请求也必须停止。系统解释无法在当前目标保持向前排序，并允许发版人显式指定更高的完整目标版本，例如 `2.9.0-alpha.1`。系统不能为了满足回退请求自行开启更高核心版本。必要语义升级要求更高核心版本、或原核心的正式版本已经占用时，正常的新目标分配按版本策略处理，与阶段回退分开判断。

每个 alpha、beta、rc 和正式产品版本属于独立的新发布身份。预发布转换为正式版必须经过新的 VERSION-only PR、合并来源与产物版本验证，不能通过重命名既有 tag、修改 Release 类型或直接把含 rc 版本及来源的字节标成正式版本实现。原运行的失败重试保留原请求、版本、来源、输入和产物；新请求产生下一个版本，不属于原身份恢复。

该决定选择保持同一目标的可预测递进和既有全局向前约束，舍弃阶段回退时自动跳到更高版本的便利。发布集合、文本请求入口及预发布部署边界由 [ADR 0017](./0017-product-prerelease-publication-boundary.md) 定义；兼容性证据仍服从 [ADR 0014](./0014-unified-product-release-version-scope.md) 的统一产品发布单元。
