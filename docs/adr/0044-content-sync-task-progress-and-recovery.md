# ADR 0044：内容仓库同步任务的逐项进度与恢复

- Status: accepted

## 背景

内容仓库的推送、拉取与合并是长批次操作，但任务表原先只有总数与聚合计数：推送不逐项推进，拉取与合并不创建任务。管理端因此无法判断批次是否在推进，刷新后也失去逐项结果。这个缺口不能靠前端定时刷新已有请求补齐，因为任务结果没有持久化，取消也没有可检查的边界。

## 决定

推送、拉取与自动合并创建同一类持久任务，使用 `content-repo` 来源并以操作类型区分；检查保持只读，不创建任务。任务的逐项状态存入独立的任务项表，任务表保存阶段、聚合计数、当前路径与附件计数；`result` 只保存提交与结果摘要，不保存附件字节。

管理端通过轻量任务进度查询轮询活动任务，而不是复用进程内的同步日志事件。任务启动是异步的：接口返回任务标识，页面按任务标识恢复；同一时刻只允许一个内容仓库任务，重复启动返回忙碌状态与在途任务标识。任务与进度 DTO 只暴露阶段、计数、仓库路径与提交摘要，不包含 owner token、宿主机路径、pid 或租约。

取消在当前处理单元结束后生效。推送在更新远端 ref 前可以取消，ref 更新后不回滚；拉取与合并保留已经完成的项。失败项重试只处理失败或未处理项。全部推送超过单批上限时按稳定路径顺序分块，每块形成一个提交，并在开始前说明分块规则与最多提交数量。

只读 GitHub 请求、树与 blob 读取、限流错误允许有界自动重试；提交与 ref 更新不自动重试，认证与权限失败不重试。

## 考虑过的方案

- **把逐项进度写进任务结果 JSON。** 被否。每次进度更新都要重写整段 JSON，失败项无法稳定索引，刷新后的重试也要重新解析和合并。
- **复用现有同步日志事件流。** 被否。事件只存在于进程内，没有持久化、重放或跨实例语义，不能作为任务状态真相。
- **取消后回滚已提交的 Git 提交。** 被否。Git 提交不可变，回滚会制造第二个提交并破坏“一批一个提交”。
- **超过单批上限时要求管理员手动分批。** 被否。已初始化的内容数量超过上限，管理员难以判断批次边界，也无法一次完成全部推送。

## 后果

- 任务表与逐项任务项表需要迁移；旧任务没有逐项记录，只能显示汇总。
- 单文件保存后的自动推送也会创建任务，历史列表需要按来源过滤，避免淹没批量任务。
- ref 更新成功但基线写入失败时，任务必须保留提交标识并阻止直接重推；需要单独的基线修复路径。
- 活动任务轮询必须与完整内容状态查询分离，避免以秒级频率触发 RAG 覆盖统计。
- 推送、拉取与合并统一以内容标识选择目标；仓库路径只用于远端新增、远端删除等没有本地内容标识的操作。
