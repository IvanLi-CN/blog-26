## GitHub 动态阅读工作区

OctoRill 面向需要持续查看 GitHub 动态的个人用户。它把发布更新、与当前用户直接相关的社交反馈、日报和收件箱入口放到同一个阅读工作区中，减少在仓库页、Release 页和通知页之间反复切换的成本。

它保留 GitHub 作为事实来源，也刻意不在站内重做完整 GitHub 工作流。用户在这里先判断“今天发生了什么、哪些内容值得继续读”，需要进行评论、合并或通知处理时再回到 GitHub。

## Release、日报与收件箱

用户可以在全部、发布、加星、关注、日报和收件箱之间切换，把 Release 更新和与自己直接相关的社交反馈收束到同一条阅读路径。Release 详情同时保留原文、翻译和润色三种阅读层，先用生成内容快速了解变化，再回到原始链接和 GitHub 上下文核对版本、发布时间与变更说明。

日报按用户时区汇总前一自然日的项目更新；当日存在获星或关注事件时，再展开对应的社交部分。用户可以从日报或收件箱直接进入 Release 和事件详情，详情按照稳定的 Release 身份读取，避免关注范围变化后已经进入阅读路径的内容突然失去上下文。

## 管理员运行面

普通用户只看到阅读工作区；管理员通过独立的后台页面维护账号、仓库和任务运行状态。用户管理页处理用户资料、角色与账号状态；仓库治理页关注订阅仓库的刷新预算、闭环进度和老化；公开 Release 页面展示公开端点自动登记的仓库与共享缓存线索。

任务中心将实时异步任务、定时任务、用户同步、订阅同步、LLM 调度、翻译调度和内容处理分别呈现。管理员可以查看排队、运行、成功、失败和取消状态，进入任务详情，并对适用任务执行重试或取消；翻译任务还可以按请求、批次、worker 和底层 LLM 调用查看诊断信息。

同步间隔、Release 抓取并发、日报自动出报时间、翻译 worker 数量和 LLM 运行参数都由后台运行时配置管理。这些控制面服务于运维和排障，不进入普通用户的主阅读路径。

## 后端聚合与外部边界

OctoRill 由 Rust/Axum 服务和 React + Vite 前端组成。浏览器只负责页面状态和交互，通过后端 API 获取业务数据；GitHub 是 Release、通知和社交活动的事实来源，LinuxDO 用于补充身份绑定，AI provider 只负责翻译与润色等生成能力。

SQLite 承担本地缓存、会话和派生数据存储，不替代 GitHub 作为事实源。后端把 OAuth、Passkey、同步、翻译、日报和后台任务装配到共享运行时，后台 scheduler 与 worker 负责推进生成任务，并把任务事件和诊断结果提供给管理员页面。

工作区的更新检查采用带 token 的签名轮询：前端定期比较 feed、日报和通知列表是否发生变化，只在有变化时重新读取对应内容；后台任务详情则通过独立的 SSE 事件流持续提供进度。这样既保持普通阅读路径的请求边界，也让管理员能够追踪长时间运行的同步和生成任务。
