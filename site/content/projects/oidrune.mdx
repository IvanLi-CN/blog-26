## 简介

Oidrune 是一个部署在 Cloudflare 上的 GitHub Actions 通知网关。

由 Oidrune 反向与 GitHub 验证调用方是否可信，大幅度简化新项目集成 Telegram 通知的配置，可实现零配置增加项目。

接入仓库只需调用固定版本的可复用 workflow，并授予 GitHub OIDC 所需的 `id-token: write` 权限。就能将结构化通知异步投递到由运营者控制的一个 Telegram 私聊、群组或频道。

## 背景与选型

最近在个人仓库内创建项目比较多，实在是受不了要给每个仓库的工作流配置通知服务，只有 GitHub 组织才能有共享的 secrets，但我不是很想为了这事创建组织。

调研了一下，发现 GitHub 支持签名的 OIDC token，这代表着 GitHub 天然提供了可信的事件发送信号，那么中继 webhook 到 Telegram 就闭环了。

为了提升可靠性，我选择了 Cloudflare Worker 提供稳定的中继服务，避免自托管中继服务导致服务中断。

### OIDC 身份与入口边界

公共入口只接受 GitHub 签名的 <a href="https://docs.github.com/en/actions/concepts/security/openid-connect" target="_blank" rel="nofollow noopener noreferrer">OIDC token</a>，并根据获批的 owner 或 repository 进行校验。入口还结合可信 workflow release SHA 和 <a href="https://docs.github.com/en/actions/concepts/runners/github-hosted-runners" target="_blank" rel="nofollow noopener noreferrer">GitHub-hosted runner</a> 约束通知来源，把调用方的信任边界收窄到可审计的工作流身份。

公共协议入口保持在 `/v1/events/workflow-completed`。<a href="https://developers.cloudflare.com/cloudflare-one/access-controls/applications/" target="_blank" rel="nofollow noopener noreferrer">Cloudflare Access</a> 只保护 `/console*` 与 `/api/admin*`，不把 OIDC 事件接收和运营控制台混成同一条访问路径。

### 接收、重试与死信

Oidrune 以持久化接收记录承接事件，再通过异步队列尝试发送通知。自动重试和死信队列保留失败事件的处理边界，运营者可以围绕接收、投递尝试和最终状态判断通知链路，而不需要把 <a href="https://telegram.org/" target="_blank" rel="nofollow noopener noreferrer">Telegram</a> 凭据下放给每个调用仓库。

### 运营控制台与生产验证

运营控制台和管理员 API 使用 GitHub-only 的 Cloudflare Access 身份。仓库同时保留一个手动触发的 `Oidrune smoke` workflow，用 GitHub OIDC 调用固定 SHA 的通知 workflow，验证公共网关返回 `202`，并继续核对对应事件是否最终由队列消费者记录为 `delivered`。
